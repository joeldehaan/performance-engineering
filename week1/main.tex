\section{Start-up Latency vs. Latency}
Latency measures the total time for a given operation, starting from when the instruction is issued and ending when it is completed. It could be a single instruction or a whole operation (e.g. writing to a file).\\

Some operations (e.g. writing to a file) may not be able to execute immediately when issued. In the case of writing to a file, the program changes to user space, reads the memory, transfers it to the I/O bus and then it is mapped to disk.

This means there is a lot of time elapsed before the actual writing to disk is performed. This time, is called the start up latency, and is the time before the actual writing is performed.

\subsection{Model}

% \[\Delta t(N)= \begin{cases}
%     a_0 N^2+c\quad\text{for }N<N_c\\
%     a_1 N^3+c\quad\text{for }N\geq N_c
% \end{cases}\]

Given two $N\times N$ matrices and their product, storing them requires a total of three $3N^2$ double precision floating point values, and performing the multiplication requires a total of $2N^3$ FLOPs (note: the factor 2 disappears if FMA is used).

As such, we decide to model the throughput $\Delta t$ of the number of floating point operations as function of the matrix rank $N$ using the following model:

\[\Delta t(N)=\frac{2N^3}{a}+c\]

% We expect that fitting the data yields a $p$ around the theoretical value 3. 
The proportionality constant $a$ exists to capture the conversion factor between the number of operations and the time they take, while the constant $c$ exists to capture any constant overhead such a operations related to the code surrounding the matrix multiplication.

% \{this model is simplified, it takes into acount memory storage, not accesses, and treats the cache influence as one singular breakpoint, independent of L2, L3.\}

\subsection{Discussion}
From observing the assembly 3 important details are noted:
\begin{itemize}
    \item The call to the matrix multiplication is inlined.
    \item There are no SIMD instructions used.
    \item There is no FMA instruction.
\end{itemize} 

The inlining makes it harder for other tools to measure performance (e.g.: it is not possible for statistical sampling of the stack frame, as there is no separate stack frame.)
As this was necessary for the perf measurements, \texttt{[[gnu::noinline]]} was used.
No vectorisation is unfortunate for performance reasons however it partially explains the appropriateness of the model.

The measured GFLOP/s is significantly lower than the theoretical maximum cpu capability. This is not surprising; no concurrency, cache tuning, vectorisation and force uninling 
means the system eventually suffers from a performance hit. 

Overall, the expected model provided a globally good fit. The data asymptotically converges to lines of gradient 3 - representing a cubic in log-log. 

In the case for $O1$ with steady clock measurements, there seems to be a jump around $N=20$ where the multiplications runs faster. Across different experinments this seems to be
reproducible. The exact reason is unknown, it could be dynamic allocations changing from regullar \texttt{malloc} to \texttt{mmap} calls, or the matrices not fitting in $L1d$ cache - however that does not
explain a performance increase.

\subsubsection{Perf}
To use perf, we used perf record -e cpu-clock:u -F 10000 --call-graph fp. A careful balance has to be struck wehre there is enough sampling to be able to obeserve the functions
but not too high that information has to be deleted. in this case we chose 10000Hz. This ended up being too low, so the results are, not only worse in general, 
but also, many of the initial results were 0, even at O0 level. For this reason, the steady clock method is significantly more representative of the acutal results.

Also due to the low sampling, and the fact that most results were very scattered, the error in this method is much larger. This is also observed in the graphs.

\subsection{Further experiments}
To determine the complete accuracy of the model and the claims, one should:
\begin{itemize}
    \item Force a function call to the matrix method and use statistical sampling whith a very high frequency of the stack frame to independently verify the time spent.
    \item Use cache simulator (like valgrind) or different architectures to test different L1d cache sizes to observe if the fluctuation region moves accordingly.
    \item track system calls to see if allocation/access schemes change.
\end{itemize}
