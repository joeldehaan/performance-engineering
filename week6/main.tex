\section{Parallelized memory access}

\textbf{(a)}
The STREAM benchmark task is embarrassingly parallel, so we expect more threads to speed it up (for example under linear scaling).
For $N = 2^{25}$ (Figure~\ref{fig:threads-2e25}) this holds for the first few threads, but then the bandwidth saturates because we run into the memory bandwidth bottleneck between RAM and the CPU.
For $N = 1024$ (Figure~\ref{fig:threads-1024}) we see a decrease instead, because the amount of work is so small that the thread overhead dominates runtime.

\textbf{(b)}
We use 6 threads (\texttt{OMP\_PLACES=cores}) and compare five settings of \texttt{OMP\_PROC\_BIND}:
\begin{itemize}
    \item \texttt{false}: threads are not bound to a specific core, so the OS may migrate them: this is flexible, but a migrated thread might lose its cached data.
    \item \texttt{true}: threads are bound to a core and never migrate: threads won't lose cached data, but the OS cannot move a thread away from a busy core.
    \item \texttt{close}: threads are placed close to the master core: this is good for threads that share chached data in L2 or L3.
    \item \texttt{spread}: threads are spread as evenly over cores: this maximises the use of hardware, but can separate threads that share data.
    \item \texttt{master}: all threads are placed on the master thread's core: this is only useful when the threads share a lot of data.
\end{itemize}
For both array sizes (Figures~\ref{fig:affinity-1024} and~\ref{fig:affinity-2e25}), \texttt{true}, \texttt{false}, \texttt{close} and \texttt{spread} perform about the same, because the number of threads is equal to the number of cores, each, there will be a one-to-one correspondence between cores and threads in all these cases.
\texttt{master} is the exception because here all threads share one core, thus, it cannot use the bandwidth of the other cores.
As such, we see a slight drop at $N = 2^{25}$, but at $N = 1024$ the drop is more severe, because additional to the waiting, the thread overhead is relatively large compared to the task size, as also stated in (a).

\section{Matrix-vector parallelisation}
To parallelise this routine a \texttt{\#pragma omp parallel schedule(static)}

With OpenMP the 3 scheduling policies are
\begin{itemize}
  \item static: assign work at compile time, threads know what they have to do. Advantage: work allocation doesn't happen at runtime. Disadvantage: if a thread stalls (goes slower than the rest) other threads in the pool can't help and just wait idle
  \item dynamic: assign each piece of work to a queue, the threads take the jobs from the queue. Advantage: minimises the chance of an idle thread. Disadvantage: while the queue can be made at compile time, popping tasks and assignation hapens at runtime
  \item guided: assign larger blocks of work at compile time. but still make threads take this pieces of work. In theory the best of both worlds but still has the overhead of a dynamical queue and stalling is still possible.
\end{itemize}

The choice depends strongly on the regularity of the workload. In this case, we are paralellising a row * column operation. Each iteration has exactly the same amount of operations (and most likely) a similar amount of memory acesses.
This is the most optimal kind of loop to allocate work statically.

After running a few runs in the cluster with the Kunpeng 920 nodes, the following results were obtained

Serial parallelisation:
    \begin{tabular}{|c|c}
          $N$ & time \\
         \hline
          1024 & 0.165 s \\
          2048 & 0.578 s \\
          4096 &  2.680 s \\
         8192 &  9.202 s  \\
         16384 & 42.931 s \\

    \end{tabular}

Dynamic parallelisation:
    \begin{tabular}{|c|c}
          $N$ & time \\
         \hline
          1024 & 0.150 s \\

The results were run on 100 cores. While it does show that the serial parallelisation is faster on the serial case for larger matrices/vectors
the results are, in general, very close to each other. This contradicts the fact that serial parallelisation has significantly less overhead.
